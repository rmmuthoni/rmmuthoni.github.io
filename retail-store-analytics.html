Retail Store Analytics

dbt, Snowflake & Power BI

An ELT workflow that loads retail data into Snowflake, transforms it through documented dbt models, and publishes analytics-ready data for Power BI.

View project source

Architecture and design

Source data is loaded before transformation. dbt manages the warehouse models and their dependencies; Power BI reads from the curated gold layer for its semantic model and reports. Stakeholders should agree on gold-model grain, relationships, and metric definitions so core business logic is not repeated across reports.

Bronze

Retains source-shaped store, customer, product, sales, and returns data.

Silver

Standardizes fields and types, removes duplicates, and validates relationships.

Gold

Organizes analytics models and reporting aggregates for downstream analysis.

Project objectives

  • Consolidate retail data in a cloud data warehouse.
  • Preserve source-shaped data with traceable, repeatable transformations.
  • Standardize data quality and business definitions across reporting.
  • Deliver documented, tested models for business analysis.

Why a layered warehouse

Retail data can be split across operational systems and use inconsistent formats or definitions. Preserving loaded inputs while centralizing cleansing and business rules gives analysis a traceable, reusable foundation for sales by store or product, customer trends, and returns, without repeating report logic.

Data flow and development lifecycle

From source loading through tested models to Power BI reporting, as described in the project README.

  1. Extract retail source data and load it into Snowflake bronze tables.
  2. Declare the loaded tables as dbt sources and configure the project connection.
  3. Build silver models to standardize fields, address duplicates and nulls, and test important keys and relationships.
  4. Build gold facts, dimensions, and aggregates with documented business rules.
  5. Use incremental models for suitable large tables to process new or changed records instead of rebuilding everything; this can reduce processing and compute as data grows.
  6. Run dbt tests and review model documentation and lineage before publishing.
  7. Connect Power BI to the gold layer, configure its semantic model and refresh, then share reports with business users.

Deployment prerequisites

The README identifies these as environment requirements; it does not prescribe a specific source system or ingestion product.

  • Access to retail source data and a functioning extraction and loading process.
  • A Snowflake account, database, schemas, warehouse, roles, and permissions for ingestion, dbt, and Power BI.
  • A compatible dbt installation with the Snowflake adapter and a securely configured connection.
  • A dbt project configured with source declarations, model settings, and environment-specific targets.
  • Power BI access, a supported Snowflake connection, and configured dataset ownership and refresh credentials.
  • Stakeholder-approved definitions for metrics such as net sales and return rate, including how discounts, taxes, cancellations, and returns are treated.

Exact versions, schemas, source systems, and ingestion tooling depend on the deployment. Keep credentials in secure environment-managed configuration, not source control. The README recommends Git for version control and review.

Incremental customer model

The public gold_customer model uses dbt incremental materialization with a merge strategy keyed by customer code.

Quality, security, and operations

Checks and operating practices called out in the project README.

Validation and lineage

  • Test critical models for non-null, unique, relationship, and accepted-value constraints.
  • Reconcile row counts and key totals against source extracts where possible.
  • Review dbt documentation and lineage before publishing.

Incremental operations

  • Monitor ingestion freshness, dbt job results, warehouse consumption, and Power BI refresh status.
  • Define handling for late-arriving data, corrections, deletes, and incremental rebuilds.
  • Choose an appropriate change-detection strategy and unique key; periodically compare incremental results with a full refresh.

Access and ownership

  • Use role-based access and expose only the sensitive customer data needed for reporting.
  • Document model owners, refresh cadence, metric definitions, and known limitations.
